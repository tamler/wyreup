# Read-only operations metrics

`GET /api/ops/metrics?since=24h` and `?since=7d` accept only `Authorization: Bearer <OPS_METRICS_KEY>`. Configure a distinct randomly generated 32-byte lowercase-hex value as the encrypted Pages secret `OPS_METRICS_KEY`; it is not an account key and cannot use the admin endpoints. Store the matching client key in the Mac Keychain as service `ops-metrics-wyreup`. Do not put it in the repository, logs, URLs or browser code. The key must be provisioned and verified through the reviewed release procedure; a missing or malformed key fails closed. Rotation requires updating both the deployment secret and local Keychain, verifying unauthorized old-key and authorized new-key responses, and retaining a secure rollback path until verification succeeds.

`functions/_lib/campaign-tags.ts` is the shared, public allowlist of non-identifying campaign labels, embedded into the static site and enforced by the server. `METRICS_REF_TAGS` is a comma-separated deployment setting selecting which of those public labels are accepted for counting and signup. To add a campaign, add its public label to the source allowlist through review, deploy the matching site and Functions, and enable it in that setting before distributing links such as `?ref=rumble`. Never use a person's name, contact details or unique identifier as a tag. Unknown labels are discarded. The browser propagates only source-allowlisted labels through same-origin links without waiting for the counter request; a label not enabled in the server setting is not counted or saved. Removing a label from the setting collapses its prior account attribution to `unknown` in reports. No ref is kept in a cookie or browser storage. The optional signup answer is a fixed choice and only daily totals are stored.

The response identifies its UTC rolling window and the wider UTC daily bucket boundaries. Daily page-load events can include repeats, bots and lost events; they do not count unique visitors. The public counter has an isolate-local token bucket and a per-tag daily cap, neither of which is a fleet-wide abuse control. Set an appropriate platform-level rate limit before relying on these numbers. No IP address is read or stored by this counter.

Signups are account rows, including accounts where key delivery subsequently failed. Activations and active-user counts cover successful hosted Pro runs only. Purchases are credit-order and subscription-invoice ledger rows at webhook processing time, not new subscribers, and are joined to the campaign tag on a newly created account. Historical untagged accounts are unknown. Subscription status is a current snapshot. Complete errors, limit hits, historical cancellation events and monetary revenue are not available in the stored data. Failed aggregate queries return an error, not zeros.

The migration and all protected Functions source must pass the existing email-auth rehearsal gate on the final deployment commit. Do not bypass or update the gate as a substitute for the required rehearsal.
